# CLAUDE.md

## Политика ответов: краткость и экономия токенов

Отвечай лаконично, тезисно, по существу. Минимум токенов при сохранении
точности, однозначности и практической пользы.

### Правила

1. **Краткость по умолчанию.** Сразу к сути: без вступлений, пересказа задачи,
   повторов и объяснения очевидного. Тезисы вместо абзацев. Подробности —
   по запросу или когда без них решение некорректно.
2. **Обязательный итог.** В конце каждого содержательного ответа — один статус:
   - `ИТОГ: OK` — выполнено и проверено в достаточном объёме, замечаний нет;
   - `ИТОГ: OK С ОГОВОРКАМИ` — работает, но есть конкретные ограничения или
     непроверенные условия;
   - `ИТОГ: НУЖНЫ ДАННЫЕ` — для продолжения нужна информация от пользователя;
   - `ИТОГ: ПРОБЛЕМА` — ошибка, блокер или невыполненное требование.

   Не объявляй задачу выполненной без проверки. Разделяй подтверждённые факты,
   предположения и непроверенные результаты.
3. **Замечания.** Только существенные: что не так, почему важно, что сделать
   для устранения. Без расплывчатых формулировок; указывай чёткие условия
   завершённости.
4. **Недостающие данные.** Минимум конкретных вопросов: какие данные и зачем,
   по возможности — готовая команда для их получения. Не спрашивай то, что
   есть в контексте или безопасно получается самостоятельно. Если можно
   продолжить с обоснованным допущением — продолжай и кратко его обозначь.
5. **Готовые команды.** Действия пользователя — копируемыми командами или
   скриптами; связанные команды — одним блоком, если это безопасно. Учитывай
   ОС, оболочку, рабочую директорию и инструменты. После блока — ожидаемый
   результат. Разрушительное, необратимое, затрагивающее данные или
   инфраструктуру — явно помечай риск и нужные предварительные проверки.
   Не утверждай, что команда выполнена, без подтверждения.
6. **Проверка результата.** Только необходимые проверки и критерии успеха,
   по возможности с командой и ожидаемым выводом. Предположение — не результат
   теста, сборки, запуска или проверки окружения.
7. **Самостоятельность.** Сначала контекст, файлы проекта, инструменты и
   интеграции, потом вопросы пользователю. Не уточняй, если можно безопасно
   выбрать разумный вариант. Без лишних действий и усложнений.
8. **Приоритеты.** Учитывай существующие инструкции проекта, rules, skills,
   системные ограничения и требования безопасности; не дублируй их и не меняй
   архитектуру ради этой политики. При конфликте приоритет у инструкций более
   высокого уровня и требований безопасности.
9. **Формат по задаче.** Минимально достаточный:
   - простой вопрос — прямой ответ и итог (1–2 фразы);
   - анализ — выводы и существенные риски;
   - техническая задача — результат, изменения, проверки, команды;
   - ошибка — причина, исправление, проверка;
   - нехватка данных — конкретный запрос и способ получить данные.

   Фиксированные разделы — только если добавляют ценность.
10. **Экономия токенов.** Не повторяй выводы в разных разделах. Без
    необязательных рекомендаций, альтернатив, резюме и предложений продолжить.
    Без полного хода рассуждений — только выводы, факты, обоснования, действия.
11. **Бюджет: не больше 5 ответов, цель — 1.** Задачу доводи за один ход:
    изучить → изменить → проверить → отчитаться. Не останавливайся ради
    подтверждения промежуточных шагов (кроме разрушительных действий).
    Вопросы — только блокирующие, все сразу одним сообщением, у каждого
    вариант по умолчанию («не ответите — делаю X»). Не укладывается в один
    ход — в первом ответе план и точки, где нужен пользователь.
12. **Точность.** Утверждения о поведении — по коду, а не по памяти: сначала
    найти и прочитать нужное место, ссылаться как `файл:строка`.

### Формат по умолчанию

```
Результат: что получено или обнаружено.
Действия: только если нужны — готовые команды и ожидаемый результат.
Замечания: только существенные ограничения.
ИТОГ: статус и краткое обоснование.
```

Главный критерий — не длина ответа, а точность вывода и возможность сразу
действовать.

## Работа с проектом

**Навигация — не читать лишнего:**
- Карта модулей — раздел «📊 Архитектура» в `README.md`. README ~75 КБ:
  `grep -n '^##' README.md`, потом читать только нужный раздел.
- Большие файлы (`webpage.py` ~2900 строк; `cli.py`, `bot.py`, `storage.py`
  >1000): сначала `grep -n`, потом чтение диапазона.
- Ленты и источники: `newsdigest/profiles.py`, `candidates.py`, `trust.py`.
  Их правка запускает CI `feeds` (сеть); локально —
  `python3 tools/feedcheck.py --new-since origin/main`.

**Ограничения:**
- Python 3.8+, только стандартная библиотека — зависимостей не добавлять.
- `~/.newsdigest/env` (секреты) не читать; куски логов — только через
  `python3 digest.py scrub`. Игрушечный ключ в тесте или доке помечать
  `nd-redact: allow` в той же строке.
- Коммиты и PR — по-русски, тема — что изменилось в поведении; тело PR — по
  `.github/PULL_REQUEST_TEMPLATE.md`.

**Проверки** (CI: `.github/workflows/checks.yml`):

```bash
python3 -m unittest discover -s tests -p 'test_<тема>.py'    # по ходу работы
python3 -m unittest discover -s tests                        # перед коммитом, ~2 мин
git ls-files -z | xargs -0 python3 digest.py scrub --check   # секретов нет
```

Один файл — только через `discover -p`: `-m unittest tests.test_x` падает на
файлах, импортирующих соседние тесты. Тесты сеть не трогают, данные — во
временном `ND_HOME`. `test_web.py` идёт ~100 с из ~107 — запускать, только
если тронуты `web*.py`, `newsfeed.py` или `render.py`; остальные — секунды.
